In CloudGround un backup conta solo dopo un ripristino di prova. La prova fa tutto quello che farebbe un
ripristino vero, tranne toccare il sito.

## Com'è fatto un backup {#anatomy}

I backup di tutti i siti vanno in un solo repository restic, fuori dal server, cifrati con la
password del repository. Un backup è fatto di più snapshot:

1. **i database**: uno snapshot per ogni database del sito, con il suo dump. `mariadb-dump` scrive in
   un canale che restic legge direttamente. Il dump non tocca mai il disco, e in particolare la
   cartella del sito, che appartiene all'utente del sito: lì potrebbe essere sostituito tra il dump e
   il backup;
2. **la descrizione del sito** (*da v1.0.0*): un file `cloudground-site.json` (vedi
   [sotto](#site-description));
3. **i file**: tutta la cartella del sito tranne `tmp/`. Lo snapshot dei file porta un'etichetta con
   l'identificativo di ogni snapshot dei database e della descrizione, e il pannello registra lo
   snapshot dei file.

Se un dump fallisce, o anche un solo file non si legge, il backup fallisce e restic dimentica gli
snapshot parziali. Eliminazione e conservazione tolgono tutte le parti insieme.

### La descrizione del sito {#site-description}

Contiene quello che serve a un altro server per creare di nuovo il sito prima di ripristinarlo:

- la release di CloudGround che ha fatto il backup;
- ID, dominio, alias, tipo, profilo della cache e versione PHP del sito;
- per un sito Node.js o Python, la versione del runtime e il comando di avvio;
- le impostazioni della cache di pagina e della object cache;
- la cartella del sito;
- ogni database del backup, con il motore (MariaDB o PostgreSQL), se è il principale e se sta su un
  server esterno;
- gli utenti database del sito su questo server, con password e privilegi.

Le password ci sono apposta. La configurazione di un'applicazione (`wp-config.php`, un `.env`)
contiene il nome del database, l'utente e la password. Un sito
[ripristinato su un altro server](/docs/data/restore-on-a-new-server) riceve gli stessi utenti con le
stesse password, quindi si collega al database senza modifiche. La descrizione è cifrata con la
chiave del repository come ogni altro snapshot, e il backup contiene comunque già i dati dei database
e, per WordPress, `wp-config.php`.

Il ripristino di prova controlla anche che la descrizione si legga. Un backup fatto prima della 1.0 non
ne ha una e viene provato come prima.

Un solo processo restic lavora su un repository alla volta, e un backup interrotto toglie il suo
blocco dal repository prima di uscire, così il backup successivo parte.

## Il ripristino di prova {#restore-test}

```mermaid
flowchart TD
  subgraph backup["Backup"]
    D["Dump del database"] -->|"via canale, mai su disco"| DS["Snapshot del database"]
    F["Cartella del sito, senza tmp/"] --> FS["Snapshot dei file, con l'etichetta del database"]
    DS --> FS
  end
  FS -->|"registrato in attesa"| T
  subgraph test["Ripristino di prova, in una cartella a parte"]
    T["Ripristina i file"] --> C1{"Cartella del sito, current su un rilascio, almeno un file?"}
    C1 -->|"sì"| C2{"Il dump è SQL e crea almeno una tabella in un database temporaneo?"}
    C2 -->|"sì"| C3{"restic check sul 10% dei dati?"}
  end
  C1 -->|"no"| KO["fallito"]
  C2 -->|"no"| KO
  C3 -->|"no"| KO
  C3 -->|"sì"| OK["riuscito, con il tempo di ripristino"]
```

La prova ripristina lo snapshot in una cartella del server riservata all'agente e controlla gli
stessi requisiti di un ripristino vero: la cartella del sito, il collegamento `current` che punta
a un rilascio che esiste nello snapshot, almeno un file. Poi legge l'inizio del dump, lo importa
in un database temporaneo con lo stesso client isolato di un ripristino, conta le tabelle (per
WordPress serve la tabella delle opzioni) ed elimina il database temporaneo. Infine `restic check`
rilegge un 10% dei dati del repository. Il tempo fino all'importazione è la stima di quanto
durerebbe un ripristino.

Regole:

- un backup nasce *in attesa* e solo la prova lo porta a *riuscito* o *fallito*;
- la prova parte nello stesso lavoro del backup e arriva in fondo anche se il lavoro viene
  interrotto; a ogni avvio il pannello rifà la prova di ogni backup rimasto *in attesa*;
- la conservazione non toglie mai il backup più recente *riuscito*, né uno *in attesa*;
- il pannello non elimina quei due backup nemmeno su richiesta.

## Il ripristino vero {#restore}

Un ripristino comincia con uno **snapshot di sicurezza** del sito com'è adesso, verificato con
la stessa prova. Se la prova fallisce, il ripristino si ferma: il sito non è stato toccato.

Poi:

- i file ripristinati vengono preparati accanto alla cartella del sito, sullo stesso disco, e
  scambiati con quella attuale in una sola operazione del kernel, quindi non c'è un momento senza sito;
- con il database (modalità *Tutto* o *Solo il database*), ogni database scelto viene salvato, svuotato e ricreato dal dump, quindi le tabelle nate dopo lo snapshot
  spariscono; gli altri database del sito non vengono toccati;
- PHP del sito riparte (svuotando la cache del codice e degli oggetti), nginx ricarica;
- se il sito non riparte, file e database tornano com'erano.

Alla fine la cache di pagina viene svuotata, ma la sua cartella resta: senza
quella cartella il sito smetterebbe di usare la cache.

## Prima di una migrazione {#before-a-migration}

*Da v0.2.0.* L'importazione di una migrazione sostituisce i file caricati e le tabelle del sito,
e un archivio vecchio o sbagliato viene importato senza errori. Comincia quindi come un
ripristino: con uno snapshot di sicurezza di tipo `pre-migration`, verificato con il ripristino di
prova. Se la prova fallisce, l'importazione si ferma prima di cambiare il sito.

Il registro dell'attività nomina lo snapshot (`safety snapshot <id> retained`). Se l'importazione
fallisce, lo snapshot resta: ripristinandolo, il sito torna com'era prima della migrazione.

Senza un repository di backup configurato l'importazione parte lo stesso, perché un server appena
installato deve poter migrare il suo primo sito. L'attività lo dice prima di toccare
qualcosa: *No backup repository is configured: no safety snapshot is taken, and this import cannot be
undone*.
