Un sito Node.js o Python fa girare la tua app come servizio a sé, con l'utente del sito e dentro i
limiti di risorse e l'isolamento del sito, come il PHP di un sito PHP. nginx gestisce
l'HTTPS e passa ogni richiesta all'app attraverso un socket unix. Rilasci, rollback e git deploy
funzionano come per i siti PHP.

## Crea il sito {#create}

1. Vai in **Siti** → **Nuovo sito** e scegli **Node.js** o **Python**.
2. Scrivi il dominio.
3. In **Configurazione** scegli il **Runtime** e, se vuoi, il **Comando di avvio**. Se lo lasci
   vuoto:
   - Node.js esegue `node server.js`;
   - Python esegue `python -m gunicorn --bind unix:$PORT --workers 2 app:app`.
4. Crea il sito.

Se il server non ha ancora quella versione, viene installata mentre il sito si crea:

- **Node.js** (20, 22 o 24): l'ultima versione di quella major viene scaricata da nodejs.org e
  verificata con i checksum SHA-256 che nodejs.org pubblica. Un file che non corrisponde viene
  scartato.
- **Python**: il Python del server, con il modulo `venv` dai pacchetti di Ubuntu.

I runtime si possono anche installare prima, in **Servizi** → **Runtime**.

Il sito nuovo mostra una piccola app di partenza con la versione del runtime. Rilascia il tuo codice
per sostituirla.

## Cosa deve fare la tua app {#your-app}

L'app deve ascoltare sull'indirizzo della variabile d'ambiente `PORT`. Di norma è il percorso di un
socket unix, che raggiunge solo nginx:

- **Node.js**: `server.listen(process.env.PORT)` (con Express: `app.listen(process.env.PORT)`).
- **Python**: `gunicorn --bind unix:$PORT app:app` o, per un'app ASGI,
  `uvicorn --uds $PORT app:app`. Avviali come `python -m gunicorn` e `python -m uvicorn`, così
  arrivano dall'ambiente virtuale del sito.

Se l'app può ascoltare solo su una porta TCP, imposta la **Porta** nella scheda **App**: l'app
ascolta allora su 127.0.0.1 e `PORT` contiene il numero. Una porta su 127.0.0.1 è raggiungibile da
qualunque processo del server, quindi usa il socket quando puoi.

L'app gira con `/srv/sites/<dominio>/current` come cartella di lavoro. Vede solo i file del proprio sito.

## Rilascio, rollback, git deploy {#deploy}

Un rilascio si costruisce dai tuoi file come per ogni sito (vedi
[rilascia una versione](/docs/data/deploy-a-release)). Prima che possa andare online, il server ne
installa le dipendenze al suo interno, con l'utente del sito:

- **Node.js**: `npm ci --omit=dev` se c'è un `package-lock.json`, altrimenti `npm install
  --omit=dev` se c'è un `package.json`.
- **Python**: un ambiente virtuale nuovo in `.venv`, poi `pip install -r requirements.txt` se il
  file c'è.

Se questo passo fallisce, il rilascio fallisce con l'output di npm o pip, e la versione online non
cambia. Attivare un rilascio, o tornare indietro, riavvia l'app sulla nuova versione. Ogni rilascio
tiene le sue dipendenze, quindi un rollback torna a ciò con cui quella versione girava.

Il git deploy funziona allo stesso modo: prima il comando di build del repository, poi le
dipendenze.

## Impostazioni, variabili e segreti {#settings}

Apri il sito e vai nella scheda **App**.

- **Runtime**, **Comando di avvio**, **Porta** e **Percorso del controllo**: salvare riavvia l'app.
- **Variabili**: variabili d'ambiente in chiaro, mostrate nel pannello.
- **Segreti**: conservati cifrati e mai più mostrati. L'app li riceve come normali variabili
  d'ambiente.

I nomi usano lettere maiuscole, cifre e `_`. Non si possono usare i nomi che il server imposta da sé,
come `PORT`, `PATH`, `HOME` e quelli che iniziano con `CG_` o `LD_`.

Sul server i valori stanno solo in un file leggibile da root, che systemd legge quando avvia l'app.
Non finiscono nel file dell'unità, nelle risposte del pannello, nel registro attività o nei log.

## Stato, riavvii e log {#health}

Il riquadro **App** dice se il servizio gira, da quando, quante volte è stato riavviato e l'esito di
un controllo (una richiesta HTTP al **Percorso del controllo** attraverso il socket). Se l'app esce o
va in crash, riparte due secondi dopo. **Riavvia** la riavvia a mano.

L'output dell'app (standard output e standard error) finisce nella scheda **Log** del sito, alla
voce **App**.

## Cosa non c'è {#limits}

- Copie di staging e pubblicazione sicura non sono ancora disponibili per i siti Node.js e Python.
- Questi siti non hanno la cache di pagina: è l'app a impostare le proprie intestazioni di cache.
- Le impostazioni PHP non si applicano.

I backup coprono tutto il sito, compresi `node_modules` o `.venv` di ogni rilascio. Un ripristino
riavvia l'app.

## Con l'API {#with-the-api}

- `GET /api/sites/<id>/app` e `PUT /api/sites/<id>/app`: le impostazioni. In `secrets` un nome
  porta il suo valore, `""` lo toglie e `••••••••` lo lascia com'è.
- `GET /api/sites/<id>/app/status` e `POST /api/sites/<id>/app/restart`.
- `GET /api/runtimes` e `POST /api/runtimes/install` con `{"runtime": "node", "version": "22"}`.
