Anyone who brute-forces passwords against SSH, `wp-login.php`, `xmlrpc.php` or the panel gets blocked
for a while: the server drops their packets on every port. A block caused by WordPress failures
keeps the address away from the sites only (ports 80 and 443). The **Blocking** page, under the
**Server** group, lists blocked and always-allowed addresses and lets you change the settings. How it works is in [address blocking](/docs/explanation/blocking).

## Automatic blocking {#automatic-blocking}

Failed sign-ins in three places count towards a block:

- **SSH**: passwords and keys that sshd rejects.
- **WordPress**: wrong passwords on `wp-login.php`, over XML-RPC and for application passwords, plus
  wrong codes for the site's [two-factor sign-in](/docs/access/wordpress-two-factor).
- **The panel**: wrong passwords and wrong two-step verification codes.

An address that crosses the threshold is blocked. The **Automatic blocking** box has these settings:

| Field | Default | Range |
| --- | --- | --- |
| **Block addresses that keep failing to sign in** | on | |
| **Failed sign-ins** | 6 | 3 to 100 |
| **Within (minutes)** | 10 | 1 to 1440 |
| **Block for (minutes)** | 60 | 1 to 43200 |

An IPv6 address is counted together with its whole /64. The box also shows which sources are being
read (**SSH: read**, **WordPress: read**, **Panel sign-in: counted**). If the server isn't enforcing
the list, the top of the page shows **The block list is not enforced**.

The following are never blocked: loopback, the server's own addresses, anything on the
always-allowed list, and Cloudflare's network (blocking one of its addresses would cut off every
visitor Cloudflare sends through it). For a site behind Cloudflare, see
[what changes for the block list](/docs/sites/behind-cloudflare#block-list).

## Always allow your own address {#allow-yours}

Do this first, so a few mistyped passwords don't lock you out.

1. Open **Blocking**. The top of the page shows **Your address**.
2. In the **Always allowed** box, press **Always allow it**, or enter an **Address or network** (an IP
   address, or a network such as `203.0.113.0/24`) and press **Allow**.

An allowed address is never blocked, no matter how many sign-ins fail from it. To remove it, press
the bin icon on its row and confirm. Its failed sign-ins start counting again.

## Block or unblock manually {#manual}

- To block, press **Block an address** in the **Blocked addresses** box, enter the
  **Address or network**, choose a duration under **For** (**One hour**, **One day**, **One week** or
  **Until removed**) and save. Packets from that address are dropped immediately, on every port.
- To unblock, press **Unblock** on its row and confirm. Packets get through again immediately, and the
  failed sign-in count resets to zero.

Each row shows **Why** (**by hand**, **SSH**, **WordPress** or **panel sign-in**) and **Until**. The
panel rejects a block that includes your address, the server, loopback, Cloudflare's network or an
allowed address, and any
block wider than /8 for IPv4 or /16 for IPv6.

## If you've locked yourself out {#locked-out}

Sign in through your provider's console and run this on the server as root:

```bash prompt
cgctl blocklist unblock <address>
```

`<address>` is your IP address. On the server, `cgctl` talks to the API socket, which has no address
that could be blocked, so the command works even if you're blocked from the panel and SSH.

## Use cgctl or the API {#with-cgctl-or-the-api}

| Command | What it does |
| --- | --- |
| `cgctl blocklist` | Prints the block list. |
| `cgctl blocklist block <address-or-network> [minutes]` | Blocks an address. Without minutes, the block lasts until removed. |
| `cgctl blocklist unblock <address-or-network>` | Removes a block. |
| `cgctl blocklist allow <address-or-network>` | Adds an address to the always-allowed list. |
| `cgctl blocklist disallow <address-or-network>` | Removes an address from the always-allowed list. |

Changes go through session-only routes. Like the token commands, `cgctl` signs in with an email and
password (plus the 2FA code), never with a token. The routes are documented in [the API](/docs/api).
