A protected path requires a username and password before anything is served. The browser shows its
own sign-in prompt, and without the right credentials the response is **401**. Each path has its own
credentials and covers everything beneath it.

Staging copies don't have this tab, because they already ask for a password on the whole site.

## Protect a path {#protect-a-path}

1. Open the site, then choose **More** and **Protected paths**.
2. Press **Protect a path**.
3. In **Path**, enter the path, such as `/wp-admin` or `/private/files`.
4. Enter a **Username** and a **Password**.
5. Press **Save**.

Protection takes effect as soon as you save: the panel rewrites the site's configuration and nginx
reloads it. If nginx rejects the configuration, nothing changes.

Rules:

- The **Path** must start with `/` and contain only letters, digits and `. _ ~ -` between slashes. It
  can't be just `/`, and it can't contain `.` or `..` segments.
- The **Username** must be 1 to 64 letters, digits or `. _ @ -`.
- The **Password** must be 8 to 72 characters.
- A site can have up to 20 protected paths.

## What protection covers {#what-it-covers}

- The path and everything beneath it. `/private` covers `/private/` and `/private/a/b.php`, but not
  `/privateer`.
- Every request, including static files, PHP scripts and pages served from the page cache.
- The panel matches against the normalized path, so a different spelling of the same path still asks
  for the same password.
- A protected path nested inside another one uses its own credentials. The longest matching path wins.
- On WordPress and WooCommerce sites, `/wp-admin/admin-ajax.php` stays open to visitors, because themes
  and plugins call it from public pages.

The panel only stores a bcrypt hash of the password, in a file that only root and nginx can read.
There's no way to read the password back: neither the panel nor the API shows it or its hash.

## Change credentials or remove protection {#change-or-remove}

- To change the username and password, press **Change** on the path's row, enter the new values and
  press **Save**.
- To remove protection, press the bin icon on the row and confirm. The path is open to everyone again.

## Use cgctl or the API {#with-cgctl-or-the-api}

```bash
printf '%s\n' "$PASSWORD" | cgctl protect add <site-id> /wp-admin <username>
cgctl protect remove <site-id> /wp-admin
```

`protect add` reads the password as a single line from standard input, never from its arguments, so
it doesn't appear in `ps` or your shell history. If the path is already protected, the command
replaces its credentials.

Through the API, use `POST /api/sites/<id>/protected-paths` with `{"path": "/wp-admin", "username": "…",
"password": "…"}`, and `DELETE` on the same URL with `{"path": "/wp-admin"}`. Both return the site's
protected paths and their usernames.
