The site shell is `bash`, running in the site's folder as the site's user. It includes `wp`,
`composer`, `git` and `php`, plus `node` if the server has it installed. Files you create get the
correct owner right away. The shell runs in the same sandbox, with the same CPU and memory limits, as
the site's PHP. Other sites and the server's configuration aren't visible, and there's no `sudo`.

:::warning[A shell key gives full control of the site]

The shell runs any command as the site's user. Anyone with a **Shell** key can read and change the
site's files and its database credentials. Only give shell keys to people you'd trust with those
files.

:::

## Turn on the shell {#turn-on-the-shell}

Only an administrator can turn it on, and only from a browser session in the panel. An API token
isn't enough.

1. Open the site and go to the **SFTP / SSH** tab.
2. Make sure **SFTP access** is on. The shell only accepts sign-ins while it is.
3. In the **SSH shell** section, turn on **Allow a shell for “shell” keys**.
4. Read the warning, which lists the keys that will be able to open a shell, and confirm.

**Connection details** now also shows the **Shell user** (`cg-shell-<id>`) and the **Shell command**.

## Add a shell key {#add-a-shell-key}

1. In the **SSH keys** section, paste the public key into **Public key**.
2. Set **Type** to **Shell**.
3. Press **Add key**.

A **Shell** key also works for SFTP. While the shell is off, it works for SFTP only and the list marks
it *shell · off*.

## Connect {#connect}

Use the **Shell command** shown in the connection details:

```bash
ssh cg-shell-<id>@<host>
```

If SSH runs on a port other than 22, the command includes `-p <port>`. An interactive session starts
in the site's `current` folder if it exists, or in the site's folder otherwise. You can also run a
single command, which starts in the site's folder: `ssh cg-shell-<id>@<host> wp --version`.

The shell accepts keys only, never a password. Each site can have at most 8 sessions open at once.
Anything a session starts, including `nohup` processes, ends when the session ends.

## Deploy a checkout as a release {#checkout-to-release}

The `~/src` folder belongs to the site user. Clone your repository there, then publish it as a
release from the **Releases** tab: in the **New release** card, choose **A checkout in ~/src** and
press **Create release**. Or use `cgctl` on the server:

```bash prompt
cgctl deploy <site-id> /srv/sites/<domain>/src/<app>
```

You promote and roll back this release like any other. The panel doesn't run anything from the
checkout: no `git` hooks, no `composer`.

## Turn off the shell {#turn-off-the-shell}

Turn off **Allow a shell for “shell” keys** and confirm. Open sessions end immediately. Keys keep
their type, and they open a shell again once you turn it back on. Pressing **Disable** on SFTP access
also ends any open shells.
