The **Firewall** page, under the **Server** group, shows whether the firewall is active and lists its
rules as the system reports them. Administrators can add and remove rules. Read-only accounts can
only view them.

The installer never turns on the firewall. Many servers already sit behind their provider's firewall,
and a script that enables ufw can lock you out, for example when SSH runs on a non-standard port. The
decision is yours. Since v0.2.0, you can make it from the panel with a single button. On a freshly
created cloud server, ufw is usually installed but off, and the page shows **inactive**. While it's
inactive, rules are saved but have no effect. The page lists them with the note
*The firewall is inactive: these rules are stored, and apply only once it is enabled.*

*Since v0.3.0.* Addresses that fail to sign in too many times are blocked through a separate
nftables table, `inet cloudground`, which doesn't depend on ufw. It works even with the firewall off.
See [Block addresses that keep failing to sign in](/docs/access/block-addresses).

## What the installer does {#installer}

- **ufw active**: it opens the ports SSH listens on (as reported by `sshd -T`, or 22 if it reports
  none), plus 80/tcp, 443/tcp, 443/udp (HTTP/3) and 8443/tcp.
- **ufw installed but off**: it changes nothing. At the end of the install, it prints the commands
  that enable ufw with SSH, the sites and the panel allowed through.
- **ufw not installed**: it does nothing.

## Turn on the firewall {#enable}

*Since v0.2.0.* You need an administrator account signed in with its own browser session. An API
token can't turn on the firewall.

1. Open **Firewall**. If ufw is installed and off, the page shows the **Turn on the firewall**
   section.
2. Review the rules it lists, each with a note on the traffic it allows:
   - The port sshd is actually listening on (as reported by `sshd -T`, or 22 if it reports none):
     *SSH, the port sshd listens on*
   - `80/tcp`: *Sites over HTTP*
   - `443/tcp`: *Sites over HTTPS*
   - `443/udp`: *Sites over HTTP/3*
   - `8443/tcp`: *This panel*
3. Press **Turn on the firewall** and confirm.

The panel adds each allow rule in order and only then enables ufw. If any rule fails, it stops and ufw
stays off. When it's done, the page shows **active** and every other incoming port is closed. The
action is recorded in the **Audit log** as `firewall.enable`, with the rules it allowed.

If SSH moved to a different port after you opened the page, the panel refuses and leaves ufw
untouched. Reload the page, review the updated rules and try again.

### Turn it on as root from the shell {#enable-from-the-shell}

You can also run the commands the installer printed, as root. They look like this, with one
`ufw allow <port>/tcp` for each port SSH listens on:

```bash prompt
sshd -T | grep '^port '
ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443/tcp && ufw allow 8443/tcp && ufw allow 443/udp && ufw enable
```

The first line shows which ports SSH uses. If it's anything other than just 22, substitute your
ports.

:::danger[Allow the SSH port first]

Running `ufw enable` without a rule for SSH's port drops your connection and blocks every future
connection to the server.

:::

Once the firewall is active, the page shows **active** and the saved rules take effect.

## Open a port {#allow-a-port}

1. Open **Firewall**.
2. In **Add or remove a rule**, set **Action** to **Allow port**.
3. Enter the **Port**, from 1 to 65535.
4. To open it to a single address only, enter the IP or network (for example `203.0.113.7` or
   `203.0.113.0/24`) in **Only from this IP**.
5. Press **Apply**.

Rules created from the panel are always TCP.

## Block a port {#deny-a-port}

Follow the same steps with **Action** set to **Deny port**. If you fill in **Only from this IP**, the
port is blocked for that address only.

## Remove a rule {#delete-a-rule}

Set **Action** to **Delete rule**, enter the same **Port** and **Only from this IP** as the rule you
want to remove, and press **Apply**. The panel removes the allow and deny rules that match exactly,
and leaves the port's other rules alone.

## Ports that always stay open {#essential-ports}

The panel rejects any rule that would lock you or your sites out:

- the ports SSH listens on (usually 22)
- 80 and 443, used by the sites
- 8443, used by the panel

You can't remove the rule for these ports or block them for everyone. You can block them for a
single address, or add allow rules.

:::warning[You can't remove a block on these ports from the panel]

The panel also rejects **Delete rule** on these ports, even for a rule that blocks a single address.
To remove one, run a command on the server as root, for example
`ufw delete deny from 203.0.113.9 to any port 8443 proto tcp`.

:::

## Use the API {#from-the-api}

`GET /api/firewall` returns the status. `POST /api/firewall/rule` with
`{"action": "allow", "port": 3306, "proto": "tcp", "from": "203.0.113.7"}` applies a rule. `action`
is `allow`, `deny` or `delete`, and `proto` is `tcp` or `udp`. Every rule is recorded in the
**Audit log**.

When ufw is off, `GET /api/firewall` also returns `plan`, the rules to allow before enabling it.
`POST /api/firewall/enable` with `{"expect": ["22/tcp", "80/tcp", "443/tcp", "443/udp", "8443/tcp"]}`
enables it. `expect` is the list you reviewed. If it no longer matches the current plan, the response
is **409**. These firewall routes only accept browser sessions. A token gets **403**.
