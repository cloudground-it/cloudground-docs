The routing is the set of `location` blocks that decides what handles each URL on the site: a front
controller, client-side routes for an SPA, real 404 pages, a proxied `/api`, redirects. It's the only
part of the vhost you can edit. The panel keeps control of TLS, certificates, logs, limits, the page
cache and its bypass rules, security headers and the PHP-FPM connection.

## Open the editor {#open-the-editor}

1. Open the site.
2. Open **More** and choose **Vhost**. Only administrators see this tab.

The **Routing and vhost** tab shows the panel-managed parts of the vhost as read-only text above and
below the editor. The editor contains the current routing, which starts out as the default for the
site type.

| Site type | Default routing |
| --- | --- |
| WordPress, WooCommerce, PHP, Laravel | `location / { try_files $uri $uri/ /index.php?$args; }` |
| Static | `location / { try_files $uri $uri/ /index.html =404; }` |
| Reverse proxy | `location /` with `proxy_pass` to the upstream, the `Host`, `X-Real-IP`, `X-Forwarded-For` and `X-Forwarded-Proto` headers, WebSocket support and a 60 s read timeout |

## Change the routing {#change-the-routing}

1. Write your blocks in the editor.
2. Choose **Save**.

The panel first checks the blocks against its rules. It then writes the vhost and runs an nginx
configuration test (`nginx -t`). If nginx accepts the configuration, the panel reloads nginx and shows
**Routing saved and live**. If nginx rejects it, the panel restores the previous files and shows the
error with the line number in your block. The site keeps running on its previous routing.

For example, routing for an SPA whose API is served by the site's app on port 3000:

```nginx
location / {
    try_files $uri $uri/ /index.html =404;
}

location /api/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
}
```

## Restore the default routing {#restore-the-default}

Choose **Restore default** and confirm. Your blocks are replaced with the default routing for the
site type.

## What the panel rejects {#what-the-panel-refuses}

Your blocks can only serve the site itself. The panel rejects the following and tells you which line
is the problem:

- Directives that aren't on its allowlist. These include `include`, logging, TLS, caching, scripting
  modules, `fastcgi_pass` and every `*_pass` directive except `proxy_pass`.
- `root` and `alias` pointing outside `<site folder>/current` or `<site folder>/releases/<name>`, or
  at a hidden folder such as `.git`.
- A `proxy_pass` to a Unix socket, one that uses a variable, or one that targets a system service port
  on this machine or on a private network (80, 443, 8443, 3306, 6379, 5252, 9080, plus any port that a
  non-site user is listening on). The site's own app, started by the site's user, is allowed.
- Paths built from client-supplied values (`$args`, `$http_*`, `$cookie_*`, `$request_uri`) and any
  `..` segment.
- `cg_*` variables, which are reserved for the panel's cache.

If a `location` or `if` block adds its own `add_header`, it still gets the panel's security headers.

A staging copy inherits production's routing, with `root` and `alias` paths rewritten to point at its
own folder.
