Every process that belongs to a site (its PHP, scheduled tasks, wp-cli and the shell) runs in the
site's systemd slice, `cg-site-<id>.slice`. The **Resources** tab shows what those processes use and
lets you cap how much they can take from other sites on the same server.

## Check a site's usage {#see-the-usage}

1. Open the site, then choose **More** and **Resources**.
2. The four values at the top show:
   - **CPU**, as a share of what the site is allowed: its quota, or all of the server's CPUs if it has
     none.
   - **Memory**, compared with its limit.
   - **Disk**, the space used by the site's folder and logs, plus the number of files.
   - **Disk IO**, bytes read and written per second.
3. Choose **24 hours** or **30 days** to set the range of the CPU and memory chart.

The panel samples the slice's counters every five minutes and measures disk usage at most once an
hour. On a new site, the first sample appears within five minutes and the first disk figure within
the hour. The panel keeps one day of samples and 30 days of hourly values.

If the kernel killed one of the site's processes for hitting the memory limit, **Memory** shows
*N processes killed at the memory limit*.

Anyone whose account can see the site can see this tab.

## Set resource limits {#set-the-limits}

You need an administrator account, since limits decide how much one site can take from all the
others.

1. On the **Resources** tab, in the **Limits** card, enter:
   - **Memory limit**, in MB.
   - **CPU quota**, as a percentage. 100 % is one CPU, 200 % is two.
   - **Process limit**.
2. Press **Apply**.

Entering 0 in a field uses the default:

| Field | Default | Allowed values |
| --- | --- | --- |
| **Memory limit** | half the server's memory, at least 1024 MB | 0, or 128 to 1048576 MB |
| **CPU quota** | no quota: the site can use every CPU | 0, or 10 to 25600 % |
| **Process limit** | 512 | 0, or 32 to 65536 |

The kernel enforces these limits on this site only. When the site reaches nine tenths of its memory
limit, it gets throttled. At the limit, the kernel ends one of the site's own processes, never one
from another site, and the site's PHP keeps serving requests. New limits take effect immediately,
without restarting anything.

There is no disk limit. You can only set an alert for disk usage (see below).

## Set usage alerts {#usage-alerts}

1. On the **Resources** tab, in the **Usage alerts** card, leave **Alert on this site's usage** on.
2. Enter the thresholds: **CPU** and **Memory** as percentages, **Disk** in MB.
3. Press **Apply**.

| Threshold | Default | When the alert fires |
| --- | --- | --- |
| **CPU** | 90 % (0 in the field) | the last three samples, covering a quarter of an hour, are all at or above the threshold |
| **Memory** | 90 % of the memory limit (0 in the field) | same as CPU |
| **Disk** | no alert (0 in the field) | the latest disk measurement is at or above the threshold |

Short spikes don't trigger an alert. The alert type is **Resources**. It appears in the **Alerts**
panel and goes to the alert webhook like any other alert (see
[alerts and notifications](/docs/server/alerts-and-notifications)). Changing thresholds doesn't touch
the site's configuration.

## Use the API {#with-the-api}

`GET /api/sites/<id>/usage?range=24h` (or `30d`) returns the samples, the limits in effect and the
latest sample. Limits and thresholds are fields of `PATCH /api/sites/<id>`:

```json
{
  "memory_max_mb": 2048,
  "cpu_quota_pct": 150,
  "tasks_max": 256,
  "usage_alerts": {"off": false, "cpu_pct": 80, "memory_pct": 90, "disk_mb": 20000}
}
```

Only administrators can send `memory_max_mb`, `cpu_quota_pct` and `tasks_max`. From any other account
the request returns **403**. `usage_alerts` is replaced as a whole. The
[site settings reference](/docs/reference/site-settings) covers every field.
