A backup is one snapshot per database (holding its dump), plus one snapshot of the site's files. Sites
without a database get the files snapshot only. Each backup then goes through a
[restore test](/docs/data/run-a-restore-test). It is *pending* until the test finishes and
counts only once it has *passed*.

## Scheduled backups {#scheduled}

Production sites are backed up daily out of the box, and each backup is kept for 30 days. Every 5
minutes the panel looks for sites that are due and starts their backups.

- Scheduled backups run only for active sites, and only once a repository and password are set.
- Staging copies are never backed up on a schedule.
- Reverse proxy sites are never backed up. They have no database, and their content belongs to the
  application behind them. Backups start switched off, and **Back up now** is refused.
- If a scheduled backup fails, the panel retries it at the site's next slot (an hour, a day or a week
  later), not at the next 5-minute check.

To change the schedule, go to the site's **Backups** tab and use the **Schedule** card:

1. Under **Frequency**, pick **Off**, **Every hour**, **Every day** or **Every week**.
2. Under **Keep**, pick how long snapshots are kept: **Keep 7 days**, 14, 30, 60, 90, 180 or 365
   days, or **Keep every snapshot**. Only administrators can change this field. If the value was set
   some other way (cgctl and the API accept 0 to 3650 days), it still appears in the list.
3. Click **Save**.

In the API: `PUT /api/sites/<site-id>/backups/policy` with `enabled`, `schedule` (`hourly`,
`daily`, `weekly`), `retention_days` and `hour`. Send only the fields you want to change. The rest
keep their current values.

### Pick a start time {#hour}

*Since v0.2.0.* Daily and weekly backups can start at a set hour.

1. Under **Frequency**, pick **Every day** or **Every week**. A **Time** field appears.
2. Under **Time**, pick the hour. The server's time zone is shown below the field, and the hour is
   in that zone.
3. Click **Save**.

The backup starts at the first 5-minute check after that hour. Weekly backups stay on the same
weekday. Changing the hour doesn't trigger a second backup on the same day. If the panel was down at
the chosen hour, the backup starts at the first check after it comes back.

**Any time** keeps the pre-v0.2.0 behavior: each backup starts a day or a week after the previous
one. In the API, `hour` takes 0 to 23, and `-1` clears it.

## Back up now {#back-up-now}

1. Open the site and go to the **Backups** tab.
2. Click **Back up now**. A *Backup started* task begins.
3. The new snapshot appears at the top of the list. Its **Restore test** column changes from
   *pending* to *passed* (or *failed*) when the test finishes.

The top of the tab shows **Last backup**, **Last restore test** and **Estimated restore time**. The
estimate is how long the restore test of the latest backup took.

```bash
cgctl --wait backup run <site-id>
```

## What gets backed up {#contents}

- Every database of the site that the panel manages on this server. The dump streams straight into
  restic and never touches the disk.
- The whole site folder, `/srv/sites/<domain>`: releases, `shared/` (configuration and uploads),
  SFTP keys and the site's `logs/` folder.
- The only thing left out is `tmp/`, where PHP keeps temporary files and sessions.

If a single file can't be read, the backup fails and isn't recorded. A partial backup never counts.

## Retention {#retention}

Once a day the panel deletes the site's snapshots that are older than the **Keep** setting (30 days
by default, never with **Keep every snapshot**). It never deletes the newest backup that passed its
restore test, or a backup whose test hasn't run yet. Retention only touches this site's snapshots
from this server.

## Delete a backup {#delete}

You need an administrator account.

1. In the **Backups** tab, click the trash icon on the snapshot's row.
2. Confirm. The snapshot and its database backup are removed from the repository.

The trash icon is disabled for the newest backup that passed its test, and for any backup whose test
hasn't run yet. The daily cleanup frees the space in the repository.
