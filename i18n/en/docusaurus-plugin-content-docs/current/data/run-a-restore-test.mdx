The panel already runs a restore test after every backup, and reruns any test left *pending* after
a restart. Run one by hand when you want to recheck an older snapshot, for example after a problem
with the repository.

## Start a test {#run}

1. Open the site and go to the **Backups** tab.
2. Click **Test restore** on the snapshot's row. A *Test restore started* task begins.
3. When the task finishes, the **Restore test** column shows *passed* or *failed*.

```bash
cgctl --wait backup verify <backup-id>
```

You can't cancel a test. Once it starts, it runs until it has a result.

## What the test checks {#checks}

The test restores the snapshot into a separate folder, never over the site. It passes only if every
one of these checks passes:

1. restic restores the snapshot's files.
2. If the site has a managed database, the linked database snapshot exists and its dump is readable.
3. The restored files contain the site folder, the `current` link points to a release that is in the
   snapshot, and there is at least one file.
4. The dump starts with SQL and imports into a temporary database, creating at least one table (the
   options table, for WordPress). The temporary database is then dropped.
5. `restic check` reads and verifies 10% of the repository's data.

The time steps 1 to 4 take is the **Estimated restore time**.

## When a test fails {#failed}

- The task fails, and its message names the check that didn't pass.
- The snapshot stays *failed*. It doesn't count as a restore point, and retention still keeps the
  newest backup that *passed*.
- Take a new backup with **Back up now** and check whether its test passes.

A failed restore test, even one inside a scheduled backup, raises an alert under the panel's bell,
for example `backup scheduled failed: restore test failed: the restored tree is empty`. See
[alerts and notifications](/docs/server/alerts-and-notifications).
