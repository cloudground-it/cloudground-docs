Quarry is CloudGround's database manager. It runs as a separate service on the panel's address, at
`/quarry`. You can open it from the panel, or sign in with a database user's name and password. For
how the two ways in and the limits work, read [How Quarry works](/docs/explanation/quarry).

## Open Quarry from the panel {#from-the-panel}

1. Open the site and go to the **Database** tab.
2. On the database's row, click **Open in Quarry**.

Quarry opens in a new tab, signed in for this site, on that database. The link works once, within 60
seconds. If Quarry says *this link to Quarry has expired or was used*, click **Open in Quarry**
again.

What you can do depends on your panel role:

- **administrator**, or **operator** assigned to the site: everything on this page. SQL editor
  statements are read-only until you turn on **Allow writes**.
- **read-only**: the table list and table structure. Rows, the SQL editor, search, export and import
  aren't available.

## Sign in as a database user {#sign-in}

1. Go to `https://<server-ip>:8443/quarry`, or `https://<panel-domain>/quarry` if the panel has a
   domain.
2. Enter the **Database user** and its **Password**.
3. Optionally, enter a **Database** to open first.
4. Click **Sign in**.

`<server-ip>` is the server's address and `<panel-domain>` is the [panel's domain](/docs/server/panel-domain).

- Only database users created by the panel can sign in: the ones in a site's **Database** tab and the
  primary users created with each site. Never `root`, and never the server's own accounts.
- You see the databases this user can open, and MariaDB checks every action against the user's
  privileges. A write by a read-only user fails with the server's error,
  `ERROR 1142 … command denied`.
- Every refusal reads *Wrong database user or password.*, whatever the actual reason. Wrong passwords
  slow down further attempts from the same network, but never lock the user out. If a network keeps
  failing, an attempt may be refused with *too many attempts for this database user at once*. Wait
  and try again. See [sign-in protection](/docs/explanation/sign-in-protection#quarry).

## Get around {#layout}

- The **sidebar** lists the databases this session can open. Under each one are its **Tables**,
  **Views** and **Routines**. **Filter tables** narrows the list. Routines are listed only: Quarry
  never runs or changes them.
- The top bar shows where you are (site › database › table) and how the session was opened:
  **database user**, **from the panel** or **from the panel, read-only**.
- A **database** has the tabs **Structure** (its tables), **SQL**, **Search**, **Export** and
  **Import**.
- A **table** has **Browse**, **Structure**, **SQL**, **Search**, **Insert**, **Export**, **Import**
  and **Operations**. Views have no **Insert** or **Import** tab.

## Browse a table {#browse}

1. Open the table, or click **Browse** on its row. You see 25 rows per page.
2. To see more at once, change **Rows per page** to 25, 50, 100, 250 or 500. The pager shows
   *Rows X–Y of N*.
3. To sort, click a column name: ascending, descending, then off. Shift-click to add more columns, up
   to four.
4. To filter, pick a column, an operator (`=`, `≠`, `<`, `≤`, `>`, `≥`, *contains*, *starts with*,
   `IS NULL`, `IS NOT NULL`) and a value, then click **Add filter**. You can add up to 16 filters, and
   a row must match all of them. **Clear** removes all filters and sorting.

Text values over 4096 bytes are truncated, and binary columns show as hexadecimal. On an unfiltered
table with more than a million rows, the total is the server's estimate. **Generated query** shows
the `SELECT` behind the current page.

## Search a database {#search}

1. Open the database's **Search** tab, enter the **Text to find** and click **Search**.
2. Quarry lists the tables with a text column that contains it, and how many rows match. Open one to
   browse just those rows.

The search stops after 200 tables or 150 seconds, and tells you when it does. A table's own
**Search** tab searches only that table.

## Edit rows {#edit}

1. In **Browse**, double-click a cell to edit its row, or click **Insert row** (the **Insert** tab
   does the same).
2. Quarry shows the SQL for the change. Confirm to run it.

Every change runs in a transaction, and is rolled back unless it affects exactly one row. To change
rows in a table without a primary key, binary columns, or values too long to edit, use the SQL
editor.

## Change the structure {#alter}

The **Structure** tab shows columns, indexes, foreign keys and the **CREATE statement**. Click **Add
column** or **Add index**, fill in the fields and click **Preview SQL**. Quarry shows the `ALTER`
before running it. On a large table, it can take a while and block writes.

## Run SQL {#sql}

1. Open the **SQL** tab and type a statement.
2. Click **Run**, or press Ctrl/Cmd+Enter.

- One statement at a time. Results are capped at 5000 rows or 8 MiB, and a statement times out
  after 60 seconds.
- From the panel, statements are read-only until you turn on **Allow writes**. Quarry then asks you
  to confirm.
- As a database user, the statement runs as that user, and MariaDB decides what it's allowed to do.
- **Explain** shows how MariaDB would run the statement (`EXPLAIN`) without running it.
- **History** lists your statements in this browser only. The panel doesn't store them.

## Simulate a write {#simulate}

**Simulate** runs an `UPDATE`, `DELETE`, `INSERT` (including `INSERT … SELECT`) or `REPLACE` inside
a transaction that is always rolled back, and tells you how many rows it would change. For a
single-table `UPDATE` or `DELETE`, it also shows up to 25 of the matching rows as they are now.
Nothing in the tables changes, so Simulate doesn't need **Allow writes**.

Quarry answers **Not simulated**, with the reason, when the statement:

- only reads (`SELECT`, `WITH`, `SHOW` …). Run it, or use **Explain**;
- commits implicitly or can't be undone: `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `RENAME`, `LOCK`,
  `SET`, `GRANT`, transaction statements, `LOAD`, `CALL` and similar;
- contains more than one statement, or an executable comment (`/*! … */`);
- calls a function that isn't a MariaDB built-in (*Simulate supports built-in functions only*), or a
  built-in that waits, locks or advances a counter (`SLEEP`, `BENCHMARK`, the lock functions,
  `LOAD_FILE`, `LAST_INSERT_ID`, the sequence functions …);
- touches a non-InnoDB table (MyISAM, Aria, MEMORY …), a view, a sequence, a table with a trigger,
  or the name of a stored routine;
- locks rows it doesn't change (`FOR UPDATE`, `FOR SHARE`, `LOCK IN SHARE MODE`), assigns a
  variable, or writes `INTO` anything other than its own table;
- runs in a session whose `sql_mode` includes `ANSI_QUOTES` or `NO_BACKSLASH_ESCAPES`.

A simulation gets 60 seconds in total, and waits at most 5 seconds for a row the live site has
locked. Afterwards, an `AUTO_INCREMENT` counter may have moved forward, as with any rolled-back
write. For the reasons behind these refusals, see [Simulate](/docs/explanation/quarry#simulate).

## Export {#export}

1. Open the **Export** tab of the database or of a table.
2. Choose a **Format**: `sql`, with the tables to include (leave empty for the whole database), or
   `csv`, for a single table.
3. Click **Start export**. A task writes the file to the site's `shared/exports/` folder.
4. Under **Exports**, click **Download**.

Exports stop at 16 GiB. When you're signed in as a database user, the export runs as that user, and
the list shows only the files you created in this session.

## Import {#import}

1. Open the **Import** tab and choose a `.sql` or `.csv` file. Click **Upload**. The file is sent in
   8 MiB chunks, up to 16 GiB, and appears under **Files to import**.
2. Click **Import** on its row.
   - For a `.sql` file, type the database name to confirm.
   - For a `.csv` file, choose the **Table for CSV imports**. The first row holds the column names,
     `\N` means NULL, and all rows are inserted in a single transaction.

:::danger[No rollback point for database users]

When opened from the panel, a `.sql` import saves the database first and restores it if the import
fails. When you're signed in as a database user, the file runs as that user, one statement at a time,
with no rollback point. If a statement fails, everything before it stays applied. Export the database
first if you might need it back.

:::

As a database user, you only see and import the files you uploaded in this session. Uploading a file
with a name that already exists is refused, so rename your file.

## Empty or drop a table {#operations}

In the table's **Operations** tab, click **Empty table** (deletes every row, keeps the structure) or
**Drop table**, then type the table name to confirm. Neither can be undone. Whether it runs depends
on the user's privileges.

## Sign out and session expiry {#sessions}

The menu in the top bar has **Sign out of Quarry**. A session also ends:

- after 30 minutes of inactivity, or 12 hours after it started;
- when the user's password is reset, or the user or site is deleted;
- when the panel restarts;
- for sessions opened from the panel: when your panel session ends, or your account loses access to
  the site.

Quarry then shows *The Quarry session has ended*, with the reason. Sign in again, or reopen it from
the panel.
