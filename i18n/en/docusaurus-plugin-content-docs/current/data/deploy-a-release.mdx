A site's code lives in releases, and a release never changes once it's created. A deploy has two
steps: **create** a release from a folder, then **activate** it. To ship changes from staging, use
[Safe Push](/docs/data/staging-and-safe-push) instead; to deploy on every push to a repository, use
[Deploy from Git](/docs/data/deploy-from-git).

## Prepare the code {#prepare}

Put the code in a folder inside the site folder, `/srv/sites/<domain>`. The easiest option is a
checkout in `~/src`, which exists while the [site shell](/docs/access/site-shell) is on:

```bash
mkdir -p ~/src/app && cd ~/src/app
git clone <repository> .
```

Over SFTP you can only write to `shared/`, `logs/`, `tmp/` and, with the shell on, `src/`. The site
folder itself is owned by root. The panel rejects folders outside the site, the site folder itself,
and `releases/`. A symlink in the folder's path (such as `current`) is followed as long as it stays
inside the site. Symlinks inside the folder are copied as symlinks, never followed.

## Create the release {#create}

1. Open the site and go to the **Releases** tab.
2. In the **New release** card, choose **A checkout in ~/src** and pick the folder under
   **Checkout**, or choose **Another folder of the site** and type the path under **Folder**.
3. Click **Create release**.

With cgctl:

```bash
cgctl --wait deploy <site-id> /srv/sites/<domain>/src/app
```

The response contains `release_id` and `deployment_id`. The new release appears in the **Releases**
tab as *created*: ready, but not live yet. While it builds the release, the panel:

- copies the folder into `releases/<release_id>`;
- links `wp-config.php` and `wp-content/uploads` to the copies in the site's `shared/` folder, so
  configuration and uploads never come from the deployed code;
- on WordPress sites, adds the panel's plugin and, if the object cache is on, its drop-in;
- precompresses CSS, JS, MJS, SVG, JSON, XML, HTML, TXT and MAP files between 1 KiB and 10 MiB;
- removes write permission for the group and for other users.

If any step fails, no release is created and the row is marked *failed*.

## Activate the release {#activate}

1. Open the site and go to the **Releases** tab.
2. Click **Activate** on the release's row and confirm.

The `current` link switches to the new release in one step, so every request is served by either the
old release or the new one. The site's PHP then reloads the code, and the page cache is purged and
rewarmed in the background. The previously live release becomes *superseded*.

In the API, activate a release with `POST /api/deployments/<deployment_id>/promote`.

## Which releases are kept {#kept}

After each activation the panel keeps the live release, every newer release, and the 5 most recent
older ones. The rest are deleted. Their rows stay in the **Releases** tab, but you can no longer
activate them.

## Next step {#next}
