Staging is a copy of production at `staging.<domain>`. It's password-protected and hidden from
search engines. Safe Push ships staging's code only after Performance Guard has measured both
versions. The reasoning behind each step is in
[Staging, Safe Push and Performance Guard](/docs/explanation/staging-and-safe-push).

## Create staging {#create-staging}

1. Open the production site and go to the **Staging** tab.
2. Click **Create staging**. A *Staging clone started* task begins.
3. When the task finishes, the tab shows the staging domain and the **User** and **Password** that
   protect it. Click **Visit** to open the site, or **Open staging** to manage it like any other
   site.

A site can have one staging copy, and a staging copy can't have its own staging. WordPress sites
with an external database can't be cloned.

Staging only gets production's **primary database**, copied into its own database
(`site_<staging-id>`, with its own user). The site's other databases aren't copied. They exist only
in production, and staging can't see them.

:::note[Staging certificate]

Staging starts without a certificate. Until you issue one, it serves the server's self-signed
fallback certificate, which browsers reject. Point `staging.<domain>` at the server too (an A or AAAA
record, or a `*.<domain>` wildcard), then click **Open staging**, go to the **SSL** tab and click
**Issue / renew**, or run `cgctl --wait cert issue <staging-id>`. **Recreate staging** creates a new
site, so you need to issue the certificate again afterwards.

:::

## Compare staging with production {#compare}

The **Staging vs production** section lists files *added*, *modified* and *removed* on staging.
Click **Refresh** after making changes. The comparison skips `wp-content/uploads` and `.git` folders,
and stops at 1000 files per list. Past that, the page shows *List truncated*.

## Publish all code {#publish-everything}

1. In the **Safe Push** panel, enter the paths to compare under **Pages to measure**, separated by
   spaces or commas (up to 10, each starting with `/`). The default is `/`.
2. Click **Publish everything** and confirm.
3. Follow the task. Performance Guard requests each page 200 times from staging and 200 times from
   production. The release is then built, put live and verified. For a page PHP renders in 60 ms,
   the whole push takes about 30 seconds. At 300 ms, expect about 2 minutes per page.
4. Open the **Releases** tab. The new release is either *live*, or *blocked* with the reason. Click
   **Guard: …** on its row to see the report.

## Publish selected files {#publish-selection}

1. In the list of differences, select the files to publish. To add a path that isn't in the list,
   type it under **Add a file or folder** and click **Add**.
2. Click **Publish selection** and confirm.

The release starts from production's code and takes only the selected paths from staging. You can't
select `wp-config.php` or anything under `wp-content/uploads`: configuration and uploads always stay
as they are in production.

## Publish database tables {#publish-tables}

Tables are copied from staging's primary database to production's. A publish never touches
production's other databases.

1. In the **Database tables** panel, select the tables (1 to 50).
2. Click **Publish tables**, type the production domain, and confirm.

Before it touches production, the panel takes a safety snapshot and runs a restore test on it. If the
snapshot fails the test, production is left as it was. Tables marked *protected live data* can't be
published: users and, on a store, orders, customers and sessions.

## Recreate staging {#recreate}

Click **Recreate staging** and type the staging domain to confirm. The current staging copy, files and
database, is deleted and replaced with a fresh copy of production.

## From the command line {#cli}

```bash
cgctl --wait staging create <site-id>
cgctl --wait safe-push <site-id> / /shop/
```

`<site-id>` is the production site's number, and the paths after it are the pages to measure.
Without paths, Performance Guard measures `/` and `/?cloudground-probe=uncached`.
