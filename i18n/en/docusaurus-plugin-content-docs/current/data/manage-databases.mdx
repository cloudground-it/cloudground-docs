A site can have any number of MariaDB databases and database users, including none. Each user signs
in with its own password and reaches only the databases you grant it, with full or
read-only access. Both are managed in the site's **Database** tab.

## What a new site comes with {#defaults}

| Type | Databases at creation |
| --- | --- |
| WordPress, WooCommerce, Laravel | one database and one user, the **primary** pair, which the site's configuration uses |
| PHP, Static | none, unless you turn on **Create a database too** when you create the site |
| Reverse proxy | none |

The primary database and primary user are marked with a **Primary** badge. You can't delete them
while the site exists, and the primary user always keeps all privileges on the primary database.

## View databases and users {#look}

Open the site and go to the **Database** tab. It has two sections:

- **Databases**: each database with its **Access** (which users can reach it, and how), **Tables**
  and **Size**. A dash means the size couldn't be read.
- **Database users**: each user with its **Access** to each database.

Read-only accounts can see both sections and open Quarry, but can't change anything.

## Add a database {#add-a-database}

1. Under **Databases**, click **Add database**.
2. Under **Name**, type a name, for example `shop_data`. The
   [naming rules](/docs/reference/database-names-and-passwords#names) apply.
3. Click **Create database**.

A task creates the database (*Creating the database …*). It starts empty and no user can reach it
until you grant access. See [change a user's privileges](#privileges).

## Add a database user {#add-a-user}

1. Under **Database users**, click **Add user**.
2. Under **User**, type a name, for example `reporting`. The same rules as for databases apply.
3. Leave **Password** empty to generate a strong one, or type your own. See the
   [password rules](/docs/reference/database-names-and-passwords#passwords).
4. Under **Privileges**, choose **None**, **Read only** or **All privileges** for each database.
5. Click **Create user**.

If the panel generated the password, the **Save the password** dialog shows the user and password
once. Copy them, then click **I have saved it**. The panel can't show the password again.

The user can only sign in from this server (`<user>@localhost`), with up to 50 concurrent
connections.

## Change a user's privileges {#privileges}

1. Under **Database users**, click **Privileges** on the user's row.
2. Choose **None**, **Read only** or **All privileges** for each database.
3. Click **Save**.

**Read only** grants `SELECT, SHOW VIEW`. **All privileges** grants `ALL PRIVILEGES` on that
database. The primary user can't lose all privileges on the primary database.

## Reset a user's password {#reset-password}

1. On the user's row, open the **⋯** menu and choose **Reset password**.
2. Choose **Generate a strong password**, or choose **Choose a password** and type one.
3. Click **Reset password**. A generated password is shown once, just like for a new user.

What happens to the site's configuration depends on the user:

- Primary user of a WordPress or WooCommerce site: the panel writes the new password to
  `wp-config.php` at the same time. If that fails, the old password is restored and the error tells
  you so.
- Primary user of any other site: the panel never writes `.env` files. Update the site's
  configuration yourself, or the site loses its database connection.
- Any other user: only the user changes. Update any application that signs in as that user.

Resetting a password also ends every Quarry session signed in as that user.

## Delete a database or user {#delete}

1. On the row, open the **⋯** menu and choose **Delete**.
2. Type the name and confirm.

- Deleting a **database** deletes all its tables and removes every user's access to it. Its backups
  stay in the repository until the retention policy removes them.
- Deleting a **user** breaks every application that signs in as that user.

The menu item is disabled for the primary database and the primary user.

## Open a database in Quarry {#open-in-quarry}

On a database's row, click **Open in Quarry**. Quarry opens in a new tab, already signed in for this
site. See [Use Quarry](/docs/data/use-quarry).

## WordPress tools {#wordpress-tools}

On WordPress and WooCommerce sites, **WordPress tools** in the **Databases** section opens three
tools that work on the primary database through wp-cli:

- **Autoloaded options**: how much data WordPress loads on every request, plus the 20 largest options.
  Anything over 800 KB slows down every uncached request.
- **Search and replace**: replaces a string across all the site's tables and keeps serialized data
  valid. GUIDs are left alone. Click **Count replacements** first, then **Replace**.
- **Expired transients**: click **Find expired transients**, then confirm to delete them.

After a replacement or a cleanup, the site's cache is refreshed.

## With cgctl {#with-cgctl}

```bash
cgctl database list <site-id>
cgctl --wait database create <site-id> shop_data
cgctl database user-create <site-id> reporting shop_data:read site_7:all
```

- `<site-id>` is the site's number.
- `database user-create` takes the user name, followed by one `<database>:all` or `<database>:read`
  for each database the user can reach. It always generates the password, which appears once in the
  output.

Deleting, changing privileges and resetting passwords are available through the [API](/docs/api):
`DELETE /api/sites/<id>/databases/<name>?confirm=<name>`,
`PUT /api/sites/<id>/database-users/<name>/grants`,
`POST /api/sites/<id>/database-users/<name>/password` and
`DELETE /api/sites/<id>/database-users/<name>?confirm=<name>`.
