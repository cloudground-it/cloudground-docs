The panel checks two things about a site: whether an installed version
has a known vulnerability, and whether any of its files match known malware. Neither check changes
the site. The panel reports, you decide. How-to guides: [Check WordPress
for vulnerabilities](/docs/access/wordpress-vulnerabilities) and [Scan a site's files for
malware](/docs/access/malware-scan).

## Vulnerability checks {#vulnerabilities}

Once a day for each site, the panel asks WordPress, inside the site's sandbox, for the versions of
core, plugins and themes. It then looks them up in WPVulnerability, a public CC0-licensed database
that aggregates several sources (CVEs and other advisories). No account or API key is needed.

- **What leaves the server:** one request per component, containing its name and version, with a
  `User-Agent` that identifies CloudGround. The domain and other server details are never
  sent.
- Responses are cached in memory for 6 hours and shared across sites. Checks run one at a time,
  each site at the hour it was first seen, so they are spread across the day.
- A version is vulnerable when it falls inside a range the database reports, using PHP's version
  comparison rules. A comparison the panel does not recognise is never counted as a
  vulnerability.
- A failed check does not wipe the previous results. It keeps them and shows the error.

The database tells you whether a version is affected, not whether your site is actually exploitable.
A plugin that is installed but deactivated can still show up.

## Malware scans {#malware}

The scan uses ClamAV without keeping it resident.

- **Nothing runs in the background.** There is no ClamAV daemon, and the signature updater daemon is
  stopped. `clamscan` starts only for a scan, as the site user, in the site's slice and sandbox, with
  a 768 MB memory cap, the lowest CPU and I/O priority, and a two-hour limit. It does not follow
  symlinks, stays on one filesystem and skips files over 25 MB.
- **A trimmed signature set.** The panel keeps the signatures that apply to website files (PHP,
  HTML, JavaScript, scripts) and drops the ones for Windows executables, documents and email, which
  take up most of the memory. It adds the PHP rules from Linux Malware Detect, which it downloads
  onto the server and does not redistribute. Signatures are updated at most once a day, right
  before a scan.
- **Staggered scans.** One scan at a time per server, once a week per site, each site at its own
  hour.
- **Quarantine** copies the file to a root-owned directory that none of the site, nginx, backups
  or SFTP can reach, then removes it from the site. If the removal fails, the copy stays and the
  operation reports a failure.

Three operations touch the system: installing the packages, reloading freshclam's
AppArmor profile, updating signatures. They run in transient units with the privileges they need,
because the agent does not have those privileges. This is the same pattern used for [PHP
extensions](/docs/sites/change-site-settings#php-extensions).

A clean scan does not prove a site is clean. Signatures only recognise malware that is already
known.
