An alert flags something that needs attention. Alerts appear in the **Alerts** panel, which
opens from the bell at the top right, and at the top of the **Dashboard**. The panel re-evaluates them
every five minutes, and immediately after any related event: a task finishing, a site changing, a
service stopping.

## What triggers an alert {#what-raises-an-alert}

| Kind | When | Level |
| --- | --- | --- |
| **Certificate** | A site's certificate failed to renew. | error |
| **Certificate** | A site's certificate expires within 14 days. | warning; error under 3 days |
| **Task** | A task failed in the last 24 hours: a backup, a restore test, a release, a site creation. | error |
| **Service** | A service is stopped or failed. | error |
| **Service** | Something is trying lots of invalid WordPress connector tokens. | error |
| **Uptime** | *Since v0.2.0.* A site with the [uptime check](/docs/sites/uptime-monitoring) on fails to respond on its public address for two checks in a row. | error |
| **Resources** | *Since v0.2.0.* A site stays above its CPU or memory threshold for 15 minutes, or its disk usage crosses its threshold (see [resource usage and limits](/docs/sites/resource-usage-and-limits)). | warning |
| **Vulnerability** | *Since v0.3.0.* A WordPress site has a known vulnerability in WordPress core, a plugin or a theme (see [check WordPress for vulnerabilities](/docs/access/wordpress-vulnerabilities)). It fires again when a new one turns up. | error if high or critical, otherwise warning |
| **Malware** | *Since v0.3.0.* The [malware scan](/docs/access/malware-scan) finds infected files on a site. | error |
| **Configuration** | Files the panel manages were changed outside the panel. | warning |
| Release | The site is serving a different release from the one on record, or a release didn't finish its post-promotion check. | warning |

Operators only see alerts for their own sites. All other roles see every alert.

*Since v0.3.0.* **Vulnerability** and **Malware** alerts name the affected components or files. Like
any other alert, they go to the notification channels and the webhook.

*Since v0.2.0.* **Task** alerts name the task in plain words, in your language (*Restore test*,
*Scheduled backup*), as the task list does, not by its internal name.

## Dismiss an alert {#dismiss}

In the **Alerts** panel, click **Dismiss** on the alert. Administrators and operators can dismiss
alerts, and a dismissed alert disappears for everyone. If the condition changes (a different renewal
error, a certificate going from warning to error) or comes back after clearing, the alert reappears.

Alerts clear themselves once the condition goes away, for example when a service starts again or a
certificate is renewed.

## Changes made outside the panel {#drift}

When someone hand-edits a file the panel manages (a site's nginx configuration, its PHP pool), the
**Dashboard** shows a **Configuration changed outside the panel** section listing every such file.
The panel hasn't overwritten anything. An administrator decides, file by file:

- **Restore**: the panel rewrites the file the way it configured it.
- **Keep**: the change stays and becomes the new expected version.

## Send notifications to a chat {#webhook}

The panel can post alerts to any webhook that accepts a `text` field, such as Slack, Discord or
Mattermost incoming webhooks.

1. Create an incoming webhook in your chat tool and copy its `https://` URL.
2. In the panel, open **Settings**.
3. In the **Notifications** section, paste the URL into **Webhook**.
4. Click **Save**.

Every five minutes, the panel sends each undismissed alert it hasn't sent in the last six hours, in
the administrators' language, formatted as `CloudGround ERROR on <site>: <text>`. So until you dismiss
an alert, it repeats every six hours. A failed send is retried on the next round. The language is
the one chosen by the first enabled administrator who set one.

The URL must use `https` (an `http://` URL is rejected when you save) and point to a public address.
When sending, the panel refuses local and private addresses, including this server's own, and
doesn't follow redirects. A send refused for that reason only shows up in the API log
(`alert webhook failed … not a public address`). Treat the URL as a credential: other accounts see it
masked, and the panel never writes it to the logs. To stop notifications, clear the field and click
**Save**.

## Webhook payload {#webhook-body}

*Since v0.2.0.* Each notification is a `POST` with a JSON body. Chat tools read `text` or `content`.
Your own code can read the `cloudground` object instead, which carries the alert's raw fields,
untranslated.

```json
{
  "text": "CloudGround ERROR on shop.example.com: Restore test failed: <error>",
  "content": "CloudGround ERROR on shop.example.com: Restore test failed: <error>",
  "cloudground": {
    "id": "<alert id>",
    "level": "error",
    "kind": "task",
    "site": "shop.example.com",
    "task_kind": "backup.verify",
    "at": "2026-10-11T03:12:00Z"
  }
}
```

| Field | Contents |
| --- | --- |
| `text`, `content` | The same message, in the administrators' language: level, site and text. Tasks are named in plain words. |
| `cloudground.id` | The alert's ID. It stays the same as long as the condition doesn't change. |
| `cloudground.level` | `error` or `warning`. |
| `cloudground.kind` | The kind: `certificate`, `task`, `service`, `uptime`, `usage`, `vulnerability`, `malware`, `drift` or `deploy`. |
| `cloudground.site` | The site's domain. Omitted for server-wide alerts. |
| `cloudground.task_kind` | Only on `task` alerts: the task's internal name, for example `backup.run`. |
| `cloudground.at` | When the alert happened, in RFC 3339 format: when the failed task started, when the site stopped responding, when the certificate expires. Can be missing. |

## Receive alerts by email {#email}

*New in v0.4.0.* Email is a second channel, next to the webhook.

1. Set the server's [mail relay](/docs/sites/send-mail-from-a-site#server-relay) in **Settings**,
   in the **Mail** card.
2. In the same card, type up to 10 addresses under **Alert emails**, separated by commas or spaces.
3. Click **Save**.

Alerts are emailed as well as sent to the webhook, if you have one. On each round the panel sends
**one message** with all the alerts it is about to notify: the subject is the alert's line when there
is only one, otherwise "3 CloudGround alerts" (for three); the body has one line per alert. The text is in the
administrators' language.

An alert counts as notified only once **every** configured channel has delivered it. If one channel
fails, the alert goes out again on the next round on every channel: no channel misses it, with a
repeat on the channel that worked.
