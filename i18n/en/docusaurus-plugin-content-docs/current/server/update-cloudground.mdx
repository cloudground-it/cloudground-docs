The panel's **Update now** button and `cgctl update` run the same update. It only installs releases
signed with a key built into the installed CloudGround, snapshots the panel's state first, and
restores the previous release automatically if the new one isn't healthy within 60 seconds.

## Check for a new version {#check}

When a newer release is out, the dashboard shows **CloudGround `<version>` is available**, along with
the version you're running and a **What's new** link. The panel checks when you open it and caches
the result for six hours.

To turn the check off, open **Settings**, go to the **Panel updates** card, switch off **Check for
updates when the panel is opened** and click **Save**. The check never installs anything on its own.

In the same card, **Update channel** controls what you're offered: **Stable** for final releases
only, or **Beta (pre-release versions too)** to include pre-releases.

From the shell, as root on the server:

```bash prompt
cgctl update --check
```

It prints `update available: <installed> -> <release> (signature verified)` or `up to date`, and
changes nothing.

## Update from the panel {#update-from-the-panel}

1. Click **Update now** on the dashboard. Or go to **Settings**, **Panel updates** card, click
   **Update now** and confirm.
2. The panel shows **Update started: the panel will restart.**

In the API: `POST /api/panel/update`, with `{"version": "<version>"}`, or `{}` for the
latest release.

## Update with cgctl {#update-with-cgctl}

On the server, as root:

```bash prompt
cgctl update
```

This installs the latest release on the panel's channel. Other forms:

| Command | What it installs |
| --- | --- |
| `cgctl update` | the latest release on the panel's channel |
| `cgctl update --to <vX.Y.Z>` | that release, and never an older one |
| `cgctl update --channel beta` | the latest release on that channel (`stable` or `beta`), this time only |
| `cgctl update --timeout <duration>` | the same, waiting that long for the result (default `10m`) |

`cgctl update` waits for the restart, then prints `updated: <previous> -> <release>` and the snapshot
it took, and exits 0. If the release was rolled back, it prints `rolled back: <previous> runs again,
with its state from <snapshot>` and exits 1.

## What an update does {#what-happens}

1. It checks the release before changing anything. The signed manifest must verify against a key
   compiled into the installed CloudGround, the release must belong to the channel (a beta never
   reaches stable), and it must be newer than both the running release and any release ever
   installed on this server.
2. It downloads every file, checks each one against the manifest, then swaps in the new binaries and
   keeps the old ones.
3. A guard process, running the previous release, stops the panel, snapshots the panel's state and
   the agent's records, and starts the new release.
4. If the agent and the panel respond on the new binaries within 60 seconds, the update is done.
   Otherwise the guard restores the previous binaries, units and snapshot, and starts the previous
   release again.

On first start the new panel migrates its database forward, step by step between the two
releases, so you can jump to any newer release in a single update. Migrations never run
backwards: the way back is the snapshot, which a failed update restores automatically.

## New system packages {#packages}

*Since v0.3.0.* A release can need a system package that older servers don't have. v0.3.0 needs
`nftables` for the [block list](/docs/access/block-addresses). Before the new release's agent starts,
a check finds which of the release's packages are missing and installs them with `apt-get`, in a
transient unit running as root. If the install fails, it runs `apt-get update` and tries once more.
The check has a 100-second time limit, within the 2 minutes the guard waits for the agent to restart.

- During an update, a failed install makes the agent fail to start. The update is then rolled back
  like any update that doesn't come up, and the previous release returns.
- On any other start (for example a reboot without network access), the check logs a warning to the
  journal with the `apt-get install` command to run, and the agent starts anyway.

The check also runs when updating from an older release, v0.2.0 included. It only needs the unit file
the new release installs.

## What an update leaves alone {#what-it-keeps}

An update replaces the binaries and, if the release changes them, the systemd units. It never touches
the sites' files, databases, certificates or backups. Sites keep serving: nginx
and the sites' PHP aren't restarted. Only the panel returns errors, for the few seconds it takes to
restart.

The update refuses to run, and changes nothing, when:

- the release isn't signed with a key built into the installed CloudGround;
- the release isn't newer than the running one or than the newest one ever installed here
  (`refusing to downgrade`);
- a backup, a restore or a task that can't resume is running. Wait for it to finish.

## Check the result {#check-the-result}

```bash prompt
cat /var/lib/cloudground-agent/update-result.json
journalctl -u cloudground-update-guard
```

The file records the version you moved to, or that the update was rolled back and why. The journal
shows every step the guard took. The three most recent snapshots are kept in
`/var/lib/cloudground-agent/update-snapshots/`.

:::note[The installer is not an update]

Running a newer release's `install.sh` on a server that already has CloudGround is refused. The error
points you to `cgctl update --to <release>`, because the installer takes no snapshot and can't roll
back. Running the installer of the release that's already installed repairs the server (see
[what the installer does](/docs/explanation/installation#rerun)).

:::
