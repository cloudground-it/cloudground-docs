Every account has exactly one of three roles. To assign roles, see [Users and roles](/docs/access/users-and-roles).

| Role | API value | Scope |
| --- | --- | --- |
| **Administrator** | `admin` | The whole server. |
| **Operator** | `operator` | Assigned sites only, plus their staging copies. |
| **Read-only** | `readonly` | Can see the whole server but cannot change anything. |

## How a request is authorized {#how-the-panel-decides}

Every request goes through these checks in order. The first check that fails determines the
response.

```mermaid
flowchart TD
  R["API request"] --> T{"Bearer cgt_… header?"}
  T -- yes --> TV{"Token valid, not expired,<br/>owner is an enabled administrator?"}
  TV -- no --> E401a["401 invalid or revoked API token"]
  TV -- yes --> SO{"Session-only route?<br/>account, users, tokens, shell,<br/>routing, firewall, panel"}
  SO -- yes --> E403a["403"]
  SO -- no --> TF
  T -- no --> S{"Cookie for a live session<br/>of an enabled account?"}
  S -- no --> E401b["401 authentication required"]
  S -- yes --> TF{"2FA required and<br/>administrator has no 2FA?"}
  TF -- "yes, outside enrollment" --> E403b["403: enroll under Security"]
  TF -- no --> P{"Role allowed<br/>by the route's rule?"}
  P -- no --> E403c["403"]
  P -- yes --> L{"Site route: is the operator<br/>assigned to the site?"}
  L -- no --> E404["404: site existence not confirmed"]
  L -- yes --> H["Request runs"]
```

A site outside an operator's scope returns **404**, not 403, so the panel does not reveal that it
exists.

## Route rules {#route-rules}

Every API route has one of these rules.

| Rule | Administrator | Operator | Read-only |
| --- | --- | --- | --- |
| open | yes | yes | yes |
| signed in | yes | yes, on assigned sites | yes |
| whole server (`global`) | yes | no | yes |
| manage (`manage`) | yes | yes, on assigned sites | no |
| administrator (`admin`) | yes | no | no |

and turning on the firewall, plus truncated scheduled task commands for read-only accounts.

*Since v0.3.0.* The rows for the block list, per-site rules, vulnerabilities, the malware scan, and
WordPress two-factor sign-in and hardening. **Check WordPress sites for known vulnerabilities** and
**Scan the sites’ files for malware every week** are panel settings, so only an administrator can
change them. Block list changes are session-only routes, like the firewall: an API token gets
**403**, and `cgctl blocklist` also signs in with an email and password.

*Since v0.9.0.* The rows for [functions](/docs/functions): a server-wide resource, so the rule is `global` for reading and `admin` for every change. An operator sees no functions, and a read-only account sees them but cannot run a test, which goes through the function itself.

## API tokens {#api-tokens}

An API token has no permissions of its own. It acts as the administrator who created it, for as
long as that owner is an enabled administrator, and is subject to the same two-step verification
rule. There are no tokens scoped to a single area. Only administrators can create tokens.

A token can never reach session-only routes: your own account (password, 2FA, sessions, profile),
users, tokens, the site shell, the routing editor, firewall rules and turning the firewall on, and
the panel's certificate and updates. It also cannot add a "shell" key. All of these return **403**.
A token cannot open Quarry either.

A database user signed in to Quarry with its own password has no panel role. Its MariaDB privileges
decide what it can do (see [How Quarry works](/docs/explanation/quarry#mariadb-decides)).

The panel revokes all of an account's tokens when its password is changed or reset, when two-step
verification is turned off, when the account is disabled, demoted or deleted, and when you run
`panel-api recover-admin`.

## Connector token {#connector-token}

Each WordPress site has a connector token, separate from user accounts. The site's plugin uses it
only to ask the panel to purge the site's pages from the cache. It grants access to nothing else.
